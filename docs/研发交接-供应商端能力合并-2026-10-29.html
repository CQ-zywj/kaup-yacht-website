2. 真实文件存储

2.1 存储结构

IndexedDB 数据库 northlink-supplier-files，version 1，两个 object store：

storekeyPath记录结构
filesid{ id, owner, name, type, size, blob }
financesupplier_id{ supplier_id, holder, bank, account, swift, proof: FileRef[] }

id 由 crypto.randomUUID() 生成；owner 为供应商 id，用于后续按供应商清理。

页面数据里不存二进制，只存引用：

{ "id": "8f1c...", "name": "bank-proof.pdf", "type": "application/pdf", "size": 182734 }

supplier_profile 中的 logo_file、banner_files[]，证书的 files[] / auth_files[]，团队头像，均为该结构（单值或数组）。读取时由 SupplierFiles.hydrate(scope) 扫描 img[data-local-file] 回填 Blob URL；SupplierFiles.links(refs, container) 渲染「查看 / 下载 / 缩略图」。

2.2 校验规则

SupplierData.fileError(file, kind) 先判类型与体积，图片再走 validateImage()：

kind允许类型体积上限附加约束
bankimage/jpeg、application/pdf5MB—
certificateimage/jpeg、image/png、application/pdf图片 5MB / PDF 10MB—
logoimage/png、image/svg+xml2MB宽高各 ≥400px
bannerimage/jpeg、image/png3MB必须正好 1920×480
teamimage/jpeg、image/png5MB—

SVG 额外做安全审查：解析后若命中 parsererror / script / foreignObject / iframe / style / animate / set，或任意节点带 on* 事件、非 # 开头的 href、url(...) 引用，一律拒绝（错误码 unsafeSvg）。

顺序约定：putMany() 先全量校验再落库，任一文件不合格则本批全部不写，避免半成品状态。

2.3 关键接口

SupplierFiles.putMany(files, owner, kind)   // 返回 FileRef[]
SupplierFiles.url(ref)                      // 返回对象 URL，带内存缓存
SupplierFiles.hydrate(scope)                // 回填 img[data-local-file]
SupplierFiles.links(refs, container)        // 渲染查看/下载/缩略图
SupplierFiles.getFinance(supplierId)        // 读银行资料记录
SupplierFiles.saveFinance(record)           // 写银行资料记录

2.4 已知限制

  • 对象 URL 只缓存在内存 Map，刷新后重新生成，长时间会话不会主动 revokeObjectURL，属可接受泄漏（原型阶段）。
  • 无配额管理。IndexedDB 超限会抛错，目前统一落到 storageError 文案。
  • 未做文件去重（同一文件多次上传会存多份）。
  • 银行资料与文件均不参与任何公开投影，见第 4、5 节。

3. 财务中心

页面 finance.html，逻辑在 js/supplier-settings.js（与店铺装修共用，靠 document.body.dataset.page === 'finance' 分派）。

字段：holder（开户名）、bank（开户行）、account（账号）、swift（可选）、proof（开户凭证，可多份，jpg/pdf/5MB）。

行为：

  1. 进入页面读 getFinance(id)，401 场景由 SupplierShell.mount() 统一拦截。
  2. 提交时校验 AccountUI.getUser() 的 id 与 role，防止跨账号写入。
  3. 未选择新文件且勾选「移除开户凭证」时清空 proof；否则沿用旧引用。
  4. 保存后 U.tr('settingsSaved') 提示，表单重建并从库中回读，确保展示的是落库结果。

隐私边界：银行资料仅存 finance store，SupplierData.publicProfile() 的白名单里没有任何银行字段，公开页与店铺页都取不到。

5. 证书可见性与公开投影

5.1 可见性判定（SupplierData.visibility(cert)）

category ∈ { company, authorization }  →  强制 private（不可通过开关放开）
其余类目                                →  cert.visibility || 'public'

证书类目常量：company / product / test / system / ip / other / authorization。

5.2 公开证书过滤（SupplierData.publicCertificates(rows, supplierId, today)）

同时满足才公开：

  1. supplier_id 匹配；
  2. 可见性为 public；
  3. status !== 'rejected'；
  4. valid_from 为空或 ≤ 今天；
  5. valid_to 为空或 ≥ 今天。

5.3 公开投影白名单（SupplierData.publicProfile(profile)）

只透出：id, company, company_en, country, city, business_type, founded, employees, intro, main_categories, tagline, theme, logo, logo_file, banner, banner_files, photos, video, team, verification_status。

不在白名单即不公开：email、phone、address、contact、position、password_hash、银行字段，以及任何 *_file 之外的凭据。company-public.html 只渲染该投影，实测公开页不出现 6222 0000 / BKCHCNBJ 等银行串。

6. 客户管理

6.1 存储与隔离

  • 键：customer_profiles:<encodeURIComponent(supplierId)>，与 rfq_drafts 解耦，不写询盘线程。
  • 每条记录：{ key, supplier_id, kind, company, country, contact, email, phone, notes, hidden }。
  • kind：manual（手工建档）或 inquiry（由询盘派生）。
  • key 规则：手工键以 manual: 开头后接 uuid；派生键以 inquiry: 开头，携带买家 id，无 id 时退化为「公司 + 国家」。
  • guard() 每次读写前校验 current_user.role === 'supplier' && current_user.id === supplierId，否则抛 customerSession。

6.2 列表合并逻辑

list(storage, supplierId, inquiries, query)：

  1. 遍历 rfq_drafts，按 inquiryKey 聚合成派生客户（同买家多条询盘合并为一条，rows 保存历史）；
  2. 叠加 customer_profiles 中的覆盖记录（手工建档、编辑过的派生客户）；
  3. 过滤 hidden；
  4. 按 company 升序；
  5. query 对 6 个字段做小写包含匹配。

6.3 校验与删除

  • company 必填；email 需通过 ^[^\s@]+@[^\s@]+\.[^\s@]+$；
  • 除 notes（5000）外字段长度 ≤300；
  • 删除为软删：写 hidden: true。派生客户软删后，询盘历史仍保留在原线程里，这也是删除提示「询盘历史已保留」的依据。

7. 文档导入与批量导入

7.1 文档导入（文章）

document-import.js：

输入处理
.docxmammoth 转 HTML；convertImage 内联为 data URL，仅接受 png/jpeg/gif/webp
.html / .htm读文本后消毒
.txt纯文本转段落
其它抛 documentFormatError

ArticleDocumentUI.bind() 在编辑器表单顶部插入导入区，选中文件后：

  1. 解析 → 填「英文标题」与预览正文；
  2. 若识别到图片，可勾选「用第一张图作为封面」；
  3. 导入模式：replace（替换标题与正文）或 append（追加到正文末尾，中间插空段）；
  4. 应用前再消毒一次，并清空对应字段的错误提示。

7.2 批量导入（表格模式）

bulk-core.js 提供纯函数：

BulkCore.parseCsv(text)              // RFC4180 风格：引号包裹、双引号转义、BOM 清理
BulkCore.mapping(header)             // 表头 → 13 个标准列，支持中文别名
BulkCore.safePath(path)              // 拒绝 .. 、隐藏文件、绝对路径与盘符
BulkCore.groups(files)               // 按文件夹把文档与图片成组
BulkCore.merge(existing, incoming)   // 按 supplier_id + import_key 去重

标准列（13）：category_id, subcategory_id, title_zh, title_en, description_zh, description_en, moq, lead_time, price_min, price_max, unit, incoterms, image。

列映射支持中文别名，例如「类别/分类/category」「中文名称/商品名称/中文标题」「起订量/minimum order quantity」「交期/lead time」「最低价/min price」「图片/image url」。

流程：上传或粘贴 → 解析 → 展示映射下拉（可改）→ 逐行校验 → 汇总「可导入 / 有问题」→ 勾选确认 → 写入 draft_products（逐行过机审，import_key 用于去重）。

限制：单文件 20MB、单次 ≤100 个条目（含 ZIP 内条目，按解压后大小估算）。

CSV 必须是标准格式：描述里含英文逗号时要用双引号包裹，否则会串列（这不是 bug，是 CSV 规范；导入页对串列行会给出「必填缺失」提示）。

7.3 批量导入（资料包模式）

bulk-materials.js：

  1. 接受 .docx/.html/.txt/.pdf/.doc 文档与图片，或 .zip（JSZip 解包）；
  2. BulkCore.groups() 按文件夹聚组：同目录下的文档 + 图片视为一个商品草稿；
  3. 每组渲染可编辑表单（标题、描述、类目、MOQ 等），逐条「校验」后批量保存；
  4. 文档解析失败的单组标记 documentFailed，不影响其它组保存。

8. 机审规则引擎

js/review-rules.js。约定：test(payload, ctx) 返回 null 表示通过，返回 { field?, detail? } 表示驳回；数组顺序即执行顺序，命中第一条即返回（只给用户一个原因，不一次驳回一串）。规则编号就是驳回码，不做二次映射。

run(target, payload, ctx) 返回：

{ "pass": false, "code": "P03", "rule": "描述长度", "message": ["描述过短…", "Description is too short…"], "field": "description_zh", "detail": "42" }

调用入口：

  • 商品提交：publish.js 调 run('product', p, { existing: siblings })，通过则 status = "active"，驳回则 status = "rejected"（内容照常落库，避免已填内容丢失），review = { code, rule, at } 一并写入。
  • 批量导入：bulk-import.js 逐行 run('product', p, { existing })。
  • 文章发布：articles.js 在 status === 'published' 时 run('article', article)，驳回则落库 rejected 并弹驳回说明。
  • 证书：目前只做表单层校验（SupplierCore.validateCert），规则引擎中的 C 系列尚未接入。

9. 未读统计口径（跨模块一致性）

多轮沟通机制上线后，未读不能再按「线程状态 = submitted」计数。统一口径：

未读 = 该线程中「对方发来 且 read_at 为空 且 type !== 'system'」的消息条数；统计前先按角色过滤可见线程：
- 供应商：row.supplier_id ? row.supplier_id === 我的id : row.mode !== 'rfq'（公开 RFQ 主帖不进任何供应商视图）
- 买家：row.buyer.id === 我的id

本轮修的两个口径问题：

14. 已知边界与后续待办

原型边界（非缺陷，上生产必须替换）
