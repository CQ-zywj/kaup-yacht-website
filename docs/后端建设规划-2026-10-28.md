## 0. 结论先行

**不要做微服务，也不要先做"大而全"的运营后台。** 这个项目的最优路径是：

> 把前端已经跑通的数据契约"提"到服务端，用**契约化单体 + 一张关系库 + 对象存储**承接，分四期上线，每期都能独立对外演示。

三个判断依据（都来自代码事实，不是经验推测）：

1. **数据契约已经存在，只是藏在浏览器里。** `accounts / supplier_profile / draft_products / rfq_drafts / certifications / articles / media_library / blog_sidebar` 这 8 个键的字段、枚举、校验规则在 `js/accounts-core.js`、`js/supplier-core.js`、`js/core.js` 里写得很完整，后端不需要重新做业务建模，只需要把它们翻译成表结构和 API。
2. **业务规则已经写好，而且是纯函数。** `js/review-rules.js`（21KB，45 条规则：已生效 15 / 业务停用 4 / 待接 OCR 与工商接口 26；二值判定 + 驳回码 + 统一社会信用代码校验位算法 + 极限词/联系方式识别）和 `js/core.js`（商品/询盘校验）不依赖 DOM，可以直接搬到 Node 服务端复用。**同一份规则前后端共用，是这个项目省时间、免"双实现漂移"的最大杠杆。**
3. **前端的数据访问已经被收敛过。** 27 个页面几乎都通过 `U.read / U.write`、`MarineAccounts.*`、`SupplierCore.*`、`CustomerCore.*` 这几个入口读写数据。改造面集中，不需要重写页面。

反过来说，**现在绝对不能做的三件事**：直接上微服务拆服务、先做审核后台和 BI 看板、把 localStorage 的数据直接 dump 成生产库。

## 2. 目标架构

```
浏览器（现有 26 页，加一层 api.js）
        │  HTTPS / JSON / 预签名直传
        ▼
   Nginx / ALB ── CDN（静态资源、图片）
        │
        ▼
  应用层：NestJS（模块化单体）
   ├─ auth      认证、会话、角色
   ├─ catalog   行业/类目/商品只读
   ├─ supplier  资料、商品、认证、文章、素材、财务、客户
   ├─ trade     询盘、会话、通知
   ├─ upload    预签名、元数据、virus scan
   ├─ review    机审（复用 review-rules）
   └─ admin     最小审核台
        │
        ├── PostgreSQL 16（主数据）
        ├── Redis（会话黑名单、限流、缓存、队列）
        ├── 对象存储（S3/OSS/MinIO，私有桶 + 签名 URL）
        └── 邮件（SES/阿里云邮件推送，走 outbox）
```

### 2.1 技术选型与理由

| 层 | 推荐 | 理由 | 备选（什么情况下换） |
| --- | --- | --- | --- |
| 语言 | TypeScript / Node 20 LTS | `review-rules.js`、`core.js`、`customer-core.js` 是纯 JS，可直接抽成 `packages/rules` 前后端共用；换语言就要写第二套规则，长期必漂移 | Java/Spring：团队以 Java 为主且已有中间件体系时选它，但机审规则要重写 |
| 框架 | NestJS（模块划分清晰）或 Fastify（更轻） | 单体内部按域分模块，未来真要拆服务时模块边界即服务边界 | — |
| 数据库 | PostgreSQL 16 | 需要 JSONB（参数、合规、i18n）、GIN 索引、`pg_trgm` 模糊搜索、行级安全；MySQL 8 也能做但 JSON 索引与全文弱一档 | MySQL：团队运维栈只熟 MySQL 时 |
| 缓存/队列 | Redis + BullMQ | 定时发布、邮件发送、图片处理、机审异步化 | — |
| 文件 | 对象存储私有桶 + 预签名 | 现状把 Blob 塞 IndexedDB，图片 base64 撑爆 localStorage 的坑必须由存储层终结 | MinIO 自建（数据不出境场景） |
| 搜索 | v1：PG `tsvector + trgm`；v2：Meilisearch | 商品量 < 5 万前不需要 ES | ES（多语言相关性调优阶段） |
| 部署 | Docker Compose 起步，单机 + 托管 PG | 首期 QPS 极低，K8s 是浪费 | K8s（多区、多租户规模化后） |

**不建议**：Serverless 全家桶（长连接、定时任务、文件处理都难受）；微服务（当前只有 1 个业务域，拆了只会增加联调成本）；MongoDB（询盘与证书是多表关联 + 状态机，关系库更合适）。

### 2.2 内容国际化怎么存

现有内容是 `{ zh: {...}, en: {...} }` 结构。**不要整块塞一个 JSONB 字段**，否则无法建索引、无法做语言维度的搜索。推荐：

- 可检索字段拆列：`title_zh`、`title_en`、`description_zh`、`description_en`
- 结构化字段用 JSONB：`parameters`、`compliance`、`trade`
- 生成列 + 索引：`to_tsvector('simple', title_zh || ' ' || title_en || ...)` 建 GIN 索引
- 语言包（437+ 个 UI 键）留在前端 `i18n.js`，不进库；只有**内容**进库

## 4. API 契约（v1）

### 4.1 约定

- 前缀 `/api/v1`，JSON，`snake_case`（与现有前端字段一致，减少改造）
- 鉴权：`Authorization: Bearer <access>`（15 分钟）+ `HttpOnly; Secure; SameSite=Lax` 的 refresh cookie（30 天）
- 分页：`?page=1&page_size=20`，响应 `{ items, page, page_size, total }`
- 错误体：`{ "error": { "code": "required", "field": "title_en", "message": "..." } }`
  **错误码直接复用现有 i18n 键**（`required` / `validEmail` / `passwordMismatch` / `customerTooLong` / `unsafeSvg` / `fileDimensionsError` …），前端拿到 code 直接 `U.t(code)` 就能显示，不需要重写提示文案
- 幂等：`POST /inquiries`、`POST /uploads/presign` 支持 `Idempotency-Key`
- 权限：所有供应商侧写操作，服务端**忽略** body 里的 `supplier_id`，一律取 token 归属；请求体带 `supplier_id` 且不匹配 → 403

### 4.2 端点清单

| 域 | 端点 | 说明 |
| --- | --- | --- |
| 认证 | `POST /auth/register`、`/auth/login`、`/auth/logout`、`/auth/refresh`、`GET /auth/me`、`POST /auth/password/forgot`、`/auth/password/reset`、`POST /auth/email/verify` | 注册区分 buyer/supplier |

### 4.3 机审接口

`POST /supplier/products/:id/submit` 内部同步执行规则链，命中第一条即返回：

```json
{ "error": { "code": "R12", "field": "description_zh",
  "message": "商品描述含联系方式（手机号 138****1234），请删除后重新提交" } }
```

规则编号即驳回码，与 `review-rules.js` 的 `id` 一一对应（S01 / R12 …）。**规则文件抽成 `packages/rules` 供前后端同时引用，版本号写进 `review_records.engine_version`。** 前端保留"发布前预检"（体验好、省一次请求），后端保留"权威判定"（不可绕过）。

## 5. 前端改造策略（27 页如何少改）

现状问题：`U.read()` 是**同步**的，改成 fetch 会牵动 26 个页面。推荐组合拳：

### 方案 A（推荐）：首屏注入 + 写走 API

1. 服务端渲染 HTML 时注入 `<script>window.__BOOTSTRAP__ = {...}</script>`（当前用户、类目、首屏列表）
2. `U.read()` 改为"先读 `__BOOTSTRAP__` / 内存快照，缺失再读 sessionStorage 缓存"，签名保持同步
3. `U.write()` / `SupplierCore.write()` / `MarineAccounts.write*()` 改为 `fetch` 写 API，**立即更新本地快照（乐观更新）+ 失败回滚**
4. 新增 `js/api.js`：统一 baseURL、token 刷新、错误码 → `U.t(code)` 映射、超时重试

好处：页面 JS 基本不动，只改 4 个文件（`common.js`、`core.js`、`accounts-core.js`、`supplier-core.js`）+ 新增 `api.js`。风险：内存快照与服务端一致性，需在关键写操作后失效重取。

### 方案 B（备选）：彻底异步化

把 `U.read` 改成 `await U.read()`，逐页改造。工作量大（26 页 × 多处），但架构更干净。**只有在 P2 之后要重构成 SPA/SSR 框架时才值得。**

### 分阶段落地顺序

| 阶段 | 前端动作 | 判定 |
| --- | --- | --- |
| P0 | 加 `api.js` + 双读（localStorage 优先，API 兜底） | 可随时回退，演示不受影响 |
| P1 | 认证切 Cookie，写操作切 API，localStorage 只留缓存 | 需要服务端稳定 |
| P2 | 删除 localStorage 直写，文件走预签名直传 | 数据不再有第二份 |
| P3 | 商品/店铺/文章页服务端渲染（SEO 刚需） | 出海流量入口 |

> 提醒：现在所有页面是 JS 渲染的空壳 HTML，**搜索引擎抓不到商品和文章内容**。出海 B2B 平台靠自然搜索获客，SSR/预渲染不是可选项，是 P3 的硬需求。

## 6. 四期路线

### P0 · 契约与骨架（约 2–3 周，1 后端 + 0.5 前端）

**目标**：把"能登录、能看商品、能发询盘"跑在真实服务端上，数据不再只在浏览器里。

| 交付 | 验收 |
| --- | --- |
| 数据契约文档（表结构 + API 契约 + 错误码表）冻结 | 前后端各自照此开发，无口头约定 |
| 项目脚手架：NestJS + PG + Redis + 对象存储 + Docker Compose + CI | `docker compose up` 一键起本地全栈 |
| 表结构与迁移（20 张表）+ 主数据种子（6 行业 / 9 分类 / 16 商品） | 种子数据与前端 mock 一致 |
| 认证全链路（注册/登录/刷新/登出/口令重置，Argon2id + Cookie） | 篡改 `current_user` 无效；跨角色 403 |
| 商品只读 API + 供应商目录 + 店铺主页只读 | 26 页里浏览类页面全部走 API |
| 询盘创建 + 买卖双方列表 + 回复 + 已读 | 完整演示路径跑通：买家发 → 供应商回 → 买家看到 |
| `js/api.js` + 双读兜底 | 服务端挂掉时原型仍可演示 |
| 越权测试用例（改 URL 里的 `supplier_id` / `product_id`） | 全部 403，不留一个后门 |

**退出条件**：关闭 localStorage 写入，演示路径仍然完整。

### P1 · 供应商运营闭环（约 3–4 周，1 后端 + 1 前端）

**目标**：供应商注册进来能真正"开店"——传资质、上商品、写文章、装修店铺。

| 交付 | 验收 |
| --- | --- |
| 文件上传：预签名直传 + 元数据 + 图片处理（sharp）+ 病毒扫描 + SVG 安全过滤 | 10MB 图片、PDF、视频都能传；危险 SVG 被拒 |
| 素材库 API + 三处引用（发布商品 / 文章封面 / 公司实拍） | 引用计数准确；删除被引用素材有提示 |
| 商品 CRUD + 状态机 + 送审 | 直接 `PATCH status=active` 被拒 |
| 认证资质：7 分类、授权文件、有效期、关联产品 | 授权类缺文件无法提交 |
| 文章：中英双版、富文本清洗、定时发布队列 | 定时到点自动转 `published`；XSS 清洗生效 |
| 店铺装修 + 财务资料（加密列） | 财务写操作有审计日志；接口不回显完整账号 |
| 工作台聚合 API（KPI + 待办 + 完善度 + 最近询盘） | 数字与列表口径一致，不再有 `--` 假数据 |
| 机审包抽离 + 服务端执行 + `review_records` | 同一份商品，前端预检与后端结论一致 |
| 客户管理 API（聚合 + 覆盖 + 隐藏） | 隐藏的询盘客户不出现在列表，但询盘本身不丢 |

**退出条件**：一个真实供应商能在无人工干预下完成"注册 → 认证 → 发商品 → 发文章 → 收到询盘 → 回复"。

### P2 · 交易强化与通知（约 2–3 周）

| 交付 | 验收 |
| --- | --- |
| 询盘升级为会话（多轮消息 + 附件） | 历史单条回复可迁移为一条 message |
| 邮件通知：新询盘、回复、审核结果、口令重置（outbox + 重试） | 发送成功率可观测，失败进死信 |
| 站内通知 + 未读角标 | 与邮件不重复打扰（可配置） |
| 搜索：PG 全文 + trgm + 同义词，排序权重对齐现有 `score()` | 中英关键词、参数搜索都能命中 |
| 最小审核台（人工复核机审驳回、证书验真、供应商认证） | 审核动作留痕，可回滚 |
| 限流 / 防刷（询盘、注册、登录） | 单 IP 每小时上限生效 |
| 举报入口 + 基础风控（同主体多账号、联系方式外链） | 触发后进待审队列 |

### P3 · 上线加固与增长（约 3–4 周 + 持续）

| 交付 | 验收 |
| --- | --- |
| 商品 / 店铺 / 文章页 SSR 或预渲染 + sitemap + 结构化数据 | 搜索引擎能抓到完整内容 |
| 可观测：结构化日志、指标（P95、错误率）、告警、慢查询 | 出事能在 5 分钟内定位 |
| 备份与容灾：PG 每日全量 + WAL 归档，对象存储版本化，季度恢复演练 | 演练通过并留档 |
| 安全：依赖扫描、越权回归集、口令策略、CSRF、CSP、上传白名单 | 渗透测试无高危 |
| 数据迁移：演示数据清洗、老账号强制改密、图片批量转存 | 迁移脚本可重复执行（幂等） |
| 合规模块：隐私政策、Cookie 同意、数据导出与删除（GDPR/ PIPL） | 法务确认口径 |
| 性能：列表页缓存、图片 CDN、DB 索引复核（目标 P95 < 300ms） | 压测报告 |

**总量级**：约 10–14 周（1.5–2 人全职），不含审核后台完整版、支付/担保交易、IM 即时通讯——这三块都是独立立项。

## 8. 风险清单

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| localStorage 迁移丢数据 | 用户抱怨"我的草稿没了" | 双读期 + 一次性导入脚本（按 `supplier_id` 归属校验）+ 只迁草稿不迁已上架 |
| 机审误杀（极限词、联系方式） | 驳回率异常高 / 供应商申诉 | 规则留档 + 白名单词表 + 人工复核入口；规则灰度上线 |
| 文件成本失控 | 视频/大图直传无限制 | 配额（供应商总容量）+ 转码 + 缩略图 + 冷存储 |
| 越权访问 | 改 URL 参数能看别人商品/询盘 | 所有查询强制注入 `supplier_id`/`buyer_id`；越权回归用例进 CI |
| i18n 内容漏译 | 中文页面出现英文占位 | 内容表双列非空约束 + 发布前检查 |
| 时区与币种 | 定时发布时间错位、报价币种混乱 | 时间统一 UTC 存储、前端按浏览器时区渲染；金额用 `numeric(14,2)` + `currency` |
| 财务资料泄露 | 银行账号明文进日志 | 加密列 + 日志脱敏 + 最小权限 |
| 合规（备案/等保/隐私） | 上线前才发现 | P1 就启动法务与备案流程，别等 P3 |

## 9. 验收标准（Definition of Done）

一期上线必须同时满足：

- 关闭 `localStorage` 写入，26 页全部功能可用
- 三种角色（访客 / 买家 / 供应商）权限矩阵全部有测试覆盖
- 关键写操作 100% 有审计日志
- 询盘全链路（发 → 收 → 回 → 读）延迟 < 2s，邮件 1 分钟内送达
- 上传 10MB 图片、PDF、视频均成功；危险文件被拦截
- 备份恢复演练通过，RPO ≤ 24h，RTO ≤ 4h
- 无高危越权与注入漏洞
