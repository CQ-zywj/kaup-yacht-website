# NORTHLINK 原型冗余与复杂度审查

| 项目 | 内容 |
| --- | --- |
| 审查日期 | 2026-10-29 |
| 代码基线 | `/Users/qiao/出海大平台/kaup-yacht-website-main`：27 页 / 46 个原生 JS / 8421 行 / 916 个文案键 / 87 项测试通过 |
| 审查范围 | 页面入口、数据写入方、校验与状态逻辑、文案资产 |
| 审查方式 | 静态阅读 + 入口计数 + 依赖反查；未做运行期性能测试 |
| 本文性质 | 问题清单与优化建议，不含代码改动 |

---

## 0. 结论

**功能数量本身不算多，问题在于"通用能力"和"具体场景"混在一起，同一件事出现了 2–4 个入口、2–4 份实现。**

三类问题按严重度排序：

| 类别 | 数量 | 后果 |
| --- | --- | --- |
| A. 入口重复、职责重叠 | 6 处 | 用户不知道该在哪操作；同一字段两处可改，容易互相覆盖 |
| B. 实现重复、口径不一致 | 5 处 | 改一处漏三处；未读、状态、校验已经开始出现分叉 |
| C. 路径过长、演示残留 | 6 处 | 单件商品的完整发布要跨 3 个页面；死代码与假数据占位 |

**最优处理顺序**：先删入口（不动逻辑）→ 再抽共享层（收口逻辑）→ 最后再谈后端化。顺序反了，冗余会被原样搬进数据库，变成"一张表三个写入方"。

## A. 入口重复与职责重叠

### A1. 店铺门面字段有三个编辑入口

| 位置 | 编辑的字段 | 问题 |
| --- | --- | --- |
| `company.html` + `js/company.js:139 storefrontEdit()` | tagline、theme、address、logo、video | 与下面重复；且这里不处理 banner，只放一个跳转链接 |
| `store-decoration.html` + `js/supplier-settings.js`（`finance ? ... : ...` 分支） | logo、banner（≤3 张）、tagline、theme | 不处理 address、video |
| `js/dashboard.js` | 只读展示 tagline | 正常 |

`company.js:186` 的编辑表单里嵌了 `${storefrontEdit(p)}`，所以 `company.html` 和 `store-decoration.html` **都会写 `supplier_profile.tagline/theme`**。两个页面各自保存时，后保存的会覆盖先保存的。

**建议**：`store-decoration.html` 作为唯一编辑入口（加 address / video 两个字段），`company.html` 里改为只读摘要 + "去装修"链接。

### A2. 同一供应商有两个对外主页

| 页面 | 内容 | 参数 |
| --- | --- | --- |
| `storefront.html` | banner 主题、认证墙、文章、商品、收藏 | `?supplier_id=` |
| `company-public.html` | 简介、公开证书、团队 | `?supplier_id=` |

两个 URL 指向同一主体，内容有交叉（认证、简介），但排版和主题完全不同。对外投放时会**互相稀释 SEO 权重**，买家也会困惑"哪个才是官网"。

**建议**：合并为一个公开页，模块化分区（简介 / 认证 / 商品 / 文章 / 团队），主题色统一。合并后正好作为后端 SSR 的落地页。

### A3. 商品有两个创建入口，批量导入还有两种模式

| 入口 | 形态 | 说明 |
| --- | --- | --- |
| `publish.html` + `js/publish.js`（366 行） | 单件，5 个 panel + 动态参数模板 + 规格行 + 证书行 + 素材选择器 | 主路径 |
| `bulk-import.html` + `js/bulk-core.js` + `js/bulk-materials.js` | 表格模式（CSV/XLSX 列映射）+ 资料包模式（ZIP/DOCX/图片成组） | 两条独立子路径 |

资料包模式面向极少数重度用户，但占了 2 个专用模块 + 1 个专用 CSS（`assets/bulk-ui.css`）。

**建议**：批量导入收进 `publish.html` 作为"批量"标签页；资料包模式先下线，等有真实用户需求再开。

### A4. 询盘有四个视图，同一线程四处渲染

| 页面 | 视角 | 读的是同一份数据 |
| --- | --- | --- |
| `inbox.html` + `js/inbox.js`（371 行） | 供应商收件箱 | `rfq_drafts` |
| `rfq-market.html` + `js/rfq-market.js`（342 行） | 供应商看公开需求 / 买家看自己的发布 | `rfq_drafts` |
| `my-rfq.html` + `js/my-rfq.js`（335 行） | 买家我的采购 + 比价 | `rfq_drafts` |
| `dashboard.js` / `accounts-ui.js` / `supplier-shell.js` | 各处未读与最近询盘摘要 | `rfq_drafts` |

统计结果：**10 个 JS 文件直接读 `rfq_drafts`**，**8 个文件各自拼状态徽章**（`statusKey`）。

**建议**：按角色只保留两个入口——
- 买家：`my-rfq.html`（我的采购，含比价），把 `rfq-market` 的"我的发布"合并进去
- 供应商：`inbox.html`（含报价）+ `rfq-market.html`（只做"发现新需求"）

### A5. 供应商侧栏 13 项，一屏放不下

`js/supplier-shell.js:3-17` 的 `ITEMS` 是 13 个：总览 / 我的商品 / 发布 / 批量导入 / 收件箱 / 认证 / 内容 / 素材 / 公司 / 装修 / 财务 / 店铺主页 / 客户。

**建议**：收到 7 项——总览、商品（发布并入）、询盘、资质（认证+公司+财务）、内容（文章+素材）、店铺（装修+主页预览）、客户。

### A6. 首页"演示采购线索"是纯填充

`js/home.js:44` 的 `PlatformContent.leads` 渲染 3 条假线索，点击进 `inquiry-detail.html`。这条链路对真实业务没有意义（真实需求走 `rfq-market`）。

**建议**：删掉该区块与 `inquiry-detail.html`（或改造为"公开 RFQ 精选"）。

## B. 实现重复与口径不一致

### B1. 同一份账号数据存两处

`js/accounts-core.js:169 writeProfile()` 会把整份公司资料**同时写进 `accounts[]` 和 `supplier_profile`**，然后用 `profile_revision` + `resolveProfile()`（`:115`）判断哪份更新，`readProfile()`（`:104`）里还有第三套兜底逻辑。

这是全站复杂度最高的地方：同一主体、两个来源、三种读取路径。

**建议**：`accounts` 只保留 id / 邮箱 / 角色 / 认证状态，资料只存 `supplier_profile` 一处。这一步做完能删掉约 60 行兼容逻辑。

### B2. 文件有两套存法

| 对象 | 存法 |
| --- | --- |
| 商品图 `draft_products[].media`、文章封面 `articles[].cover` | 路径字符串或 base64 DataURL |
| logo / banner / 证书 / 银行凭证 | IndexedDB Blob + 引用 `{id,name,type,size}`（`js/supplier-files.js`） |

同是"一张图"，两种模型并存。`supplier-shell.js:105 mediaPicker()` 取值时还要 `row.url || row.name` 双重兜底。

**建议**：统一为 asset 引用（对象存储的 `asset_id`），`media` 与 `cover` 都改存 id。这也是后端化的前置条件。

### B3. 证书有两套模型

- 商品内嵌：`draft_products[].certifications[]` = `{type, number, image}`
- 全局证书：`certifications[]` = 7 分类 + 有效期 + 验真 + `product_ids` 关联

`docs/未实现功能清单.md` 自己也标注过"不能直接复用"。现在两套同时存在，商品详情的证书区要合并两个来源（`js/supplier-display.js`）。

**建议**：全局 `certifications` 为唯一事实源，商品只存 `cert_ids`。内嵌结构迁移后废弃。

### B4. 校验分散在五处

| 位置 | 校验内容 |
| --- | --- |
| `js/core.js:76 validateProduct()` | 中英标题/描述、涂装 6 项合规 |
| `js/review-rules.js`（437 行） | 机审 P01–P17 / A01–A06 / S / C / M 系列 |
| `js/supplier-core.js:95/110/123` | `validateCert` / `validateArticle` / `validateMedia` |
| `js/supplier-data.js:18 fileError()` | 上传类型与体积 |
| 各页面表单内联 | 空值、价格、日期区间 |

同一商品要过 `validateProduct` 和 `run('product')` 两道，规则有重叠（P01 必填 vs validateProduct 必填），报错文案来源不同。

**建议**：只保留 `review-rules` 为判定入口，其余降级为"规则前置提示"；`fileError` 并入规则包作为 M 系列。

### B5. 未读统计三处各写一遍

`js/accounts-ui.js`、`js/supplier-shell.js:37 unreadInquiries()`、`js/dashboard.js` 各自过滤一遍，`supplier-shell` 里甚至保留了"没有 `MarineMessages` 时"的手写 fallback 分支——说明这三处历史上已经不一致过。

**建议**：只在 `messages-core.js` 导出一个 `unreadTotal(rows, role, scope)`，其余全部调用它。这也是后端 `/notifications/unread` 端点的口径来源。

## C. 路径过长与演示残留

### C1. 发布一件商品的完整路径跨 3 个页面

`publish.html`（5 段表单 + 机审）→ `media-library.html`（选图）→ `supplier.html`（上下架）。

且发布时的机审是二值判定：驳回则 `status = rejected`，用户要回表单改完**重新提交**，没有"字段级就地修正"。

**建议**：改成 3 步向导（基本信息 → 参数与图片 → 价格与提交），机审驳回定位到具体字段并在当前页高亮，不跳页。

### C2. 询盘流程对 1–2 人的小供应商过重

供应商侧完整动作：收件箱 → 点开会话 → 标记已读 → 回复或报价 → 分配业务员 → 接受/关闭。

其中"分配业务员"（`js/messages-core.js:217 assign` / `:227 autoAssign`）依赖硬编码的 3 人名单（`:6 MEMBERS`），对多数供应商是纯负担。

**建议**：分配默认隐藏，供应商 ≥3 个成员时才出现；`MEMBERS` 改为可配置的成员表。

### C3. 买家与供应商角色不能共存

README 明确写："该原型的所有标签页共享同一个登录态；买家与供应商切换需要重新登录。"

真实场景里"工厂自己也采购"很常见，每次切角色都要重登，演示和自测成本都高。

**建议**：账号支持 `buyer + supplier` 双角色，顶栏一个切换器。

### C4. 死代码与演示分支

| 位置 | 内容 | 判断 |
| --- | --- | --- |
| `js/messages-core.js:272 toPublicRfq()` | 注释写"1440 分钟无人回复 → 生成公开 RFQ 草稿（演示手动触发）" | 无调度器，实际无调用方，属死代码 |
| `js/messages-core.js:6 MEMBERS` | 硬编码 3 个业务员 | 应由数据驱动 |
| `js/core.js:59-60` | `status === "published"` / `"pending"` 的旧数据兼容 | 可保留但应打标记，下一版移除 |
| `js/supplier-core.js:196 seedDemo()` | 演示种子（4 证书 / 3 文章 / 5 素材） | 建议只在 `?demo=1` 时触发，不要每次进控制台都跑 |

### C5. 文案资产偏胖

916 个键中，静态可检出引用的约 385 个（其余 531 个中，一部分确实通过变量动态取用，例如 `STATUS_KEY` 映射，但仍存在成批废弃文案）。

**建议**：加一个 `npm run i18n:audit`（Node 脚本，无需依赖）定期比对键与引用，人工确认后清理。这一步对后端化也有价值——错误码要复用这些键。

### C6. 机审 17 条商品规则只有 7 条生效

已实现：P01–P04 / P09 / P16 / P17。
已停用：P07（联系方式）、P08（极限词）——业务决定允许站外联系方式。
待实现：P05 / P06 / P10 / P11 / P12 / P13 / P14 / P15 / P18。

其中 **P05（数量与交期）、P06（HS 编码）、P10（图片短边 ≥800px）、P11（单张 ≤5MB）、P18（视频规格）** 不需要 OCR 或工商接口，纯逻辑即可实现，建议优先补；P07/P08 做成服务端开关而非删除代码。

## E. 与后端化的关系

这份清单不是"顺手优化"，而是**后端化的前置条件**。原因：

- 文件两套存法 → 服务端会出现"URL 字符串"和"asset_id"两种外键，迁移时必然要写两套兼容
- 证书两套模型 → 会变成两张证书表，商品关联关系重复
- 账号双写 → 会变成两张主体表 + 同步逻辑，是最容易产生脏数据的结构
- 10 个文件读同一份数据 → 会变成 10 处缓存失效点

**建议顺序：第一档 → 第二档 → 再接后端**。第二档做完，数据模型基本就是服务端想要的样子，后端化会顺很多。
