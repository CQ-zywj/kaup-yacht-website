# 买卖双方平台优化审查

日期：2026-10-08。依据现有页面、脚本、已保存页面截图和 ECHEMI 公开导航进行审查。本文件是下一阶段建议，不代表原 PRD 的新增验收要求，也不声称已实现这些功能。未读取 ECHEMI 登录后的私有功能，未推断其内部后端实现。

## 结论

当前原型完成了商品发现、发布和询盘演示。下一步应优先补齐公共采购门户、买家工作台、卖家工作台及询盘会话模型；视觉调整与后端准备围绕这些业务流程展开。

## 已确认的现状

| 位置 | 现状 | 下一阶段影响 |
| --- | --- | --- |
| js/rfq.js | 询盘没有 buyer_user_id、buyer_company_id、seller_company_id；通用需求没有需求标题或类目；成功后引导至 inbox.html | 无法确定询盘归属，通用需求难以分发，买家误入卖家收件箱 |
| js/inbox.js | 展示 rfq_drafts 全部条目；打开条目修改共用状态 | 所有卖家收到同一批询盘；需要参与企业权限和逐用户已读记录 |
| js/core.js replyRfq | 保存单个 reply 对象 | 再次回复覆盖前一条，不能保留多轮沟通和报价版本 |
| js/supplier.js | 展示本浏览器所有商品草稿，仅有编辑入口 | 没有企业商品归属、上下架、审核、批量管理及业务统计 |
| js/common.js、js/product.js | 商品国家和美元符号固定展示，供应商信息嵌入商品 | 多国卖家、多币种接入后显示不准确，企业资料更新易不一致 |
| js/common.js | 页面调用同步 U.read/U.write/U.products | 将来网络请求不能直接替换同步调用，需要统一异步数据层 |
| js/home.js | 精选商品使用固定商品 ID | 需要运营配置和失效商品处理 |

这些是原型与未来平台的差距，并非全部属于当前静态 PRD 的缺陷。

## 优先优化的页面

1. 公共导航：商品、供应商、采购需求；账户入口提供买家中心、卖家中心。登录后根据企业权限显示工作台，可兼具买卖身份。静态版提供明确标注的演示身份切换。
2. 买家中心：我的采购需求、发出的询盘、收到的报价、会话消息、收藏与对比、企业资料。询盘成功返回买家询盘详情，展示收件企业、提交时间和后续操作。
3. 卖家中心：待回复询盘、我的报价、商品管理、企业店铺、资质文件、成员权限。商品管理改为可筛选表格，支持草稿、待审核、已上架、驳回、已下架以及编辑、预览、复制、上下架。
4. 供应商列表与公开店铺：按企业类型、国家、主营类目和认证筛选；店铺展示简介、主营商品、生产或服务能力、资质及联系入口。公开店铺与 seller 工作台分开，supplier.html 当前用途是商品管理。
5. 采购需求大厅：公开需求展示标题、类目、数量单位、市场、交期、有效期及附件概况；卖家提交结构化报价。买家公司公开信息与私人联系方式分开。
6. 会话与报价详情：双向消息时间线、附件、报价版本、报价有效期；买家比较报价或继续沟通，卖家补充规格与条款。

## 船舶行业采购信息

- 整艇：新建/二手、制造年份、交付地点、定制方式、艇型、主要尺寸、材质、动力、载员和适用用途；按供给类型选择相关字段。
- 设备：品牌、型号、适配艇型、关键性能、保修、备件与交期。
- 涂装：适用部位、包装单位、施工条件、技术资料和安全资料；文件带版本与日期，企业认证与产品证书分别呈现。
- 服务：服务地区、港口、服务能力、排期和计价方式。
- 贸易字段：币种、价格方式（范围/起价/面议）、计价单位、最小起订量、交付港口、贸易条款和付款条件。整艇和项目服务支持面议，数量单位随品类变化。

证书页面可设计编号、颁发机构、有效期、适用产品及平台核验状态。行业字段和合规要求在生产上线前由业务负责人确认，本次不作法律合规判断。

## 后端接入前的数据和接口准备

建议拆分 User、Company、CompanyMembership、Product、ProductTranslation、Certification、FileAsset、BuyingRequest、Inquiry、Conversation、Message、Quote、QuoteItem、Favorite、Notification 等实体。用户通过企业成员关系获得买家或卖家权限，商品归属企业。

采购需求生命周期、询盘跟进状态、消息已读和报价状态分别保存。定向商品询盘有明确收件卖家；公开采购需求可产生多个卖家的独立报价或会话，各卖家不能读取竞争方私有内容。同一采购需求支持汇总比较报价。

页面通过统一 Promise 接口访问数据，例如 productRepository.list/get/save、inquiryRepository.create/list、messageRepository.list/send、quoteRepository.create。静态实现使用模拟仓库；后端实现使用 API 仓库。UI 预留加载、失败、空数据、重试、提交中、禁止重复提交及编辑冲突处理。

文件使用 asset_id、文件名、大小、类型、用途和访问权限，真实内容由文件服务保存。后端决定私有附件的访问权，不能仅依赖前端隐藏按钮。商品发布、认证核验、询盘收件企业与权限均由服务端校验；公开需求不应自动广播敏感联系人资料。

建议先定义分页响应、筛选参数、错误格式和实体 ID，再接入数据库。localStorage 仅保留演示数据及必要的本地未提交表单，不作为生产业务数据源。无需为了接口接入先重写成框架；待会话、权限和工作台范围明确，再评估框架迁移。

## 视觉与交互

现有海事配色和品牌风格可保留。首页缩减首屏宣传区域，让类目、商品/供应商/采购需求搜索切换、精选供应商和近期采购需求更早出现。商品卡增加关键参数、价格单位、供应商地区、收藏与对比；产品图片换成具有来源授权的真实内容。手机端详情设置便于触达的询盘入口，工作台重点展示待办。

发布流程拆为基础信息、技术规格、贸易与文件、预览提交；显示完成度并保存各步骤草稿。为长表单增加错误摘要和首个错误定位。未认证、无报价、审核驳回、资料过期、附件上传失败均提供明确的下一步。

## 建议迭代顺序

第一阶段：演示身份、买家中心、卖家中心、供应商店铺、带收件企业的双向会话；演示两家买家与两家卖家，验证数据隔离和多轮回复。

第二阶段：采购需求大厅、结构化报价和比较、商品状态管理、收藏对比、分步骤发布。

第三阶段：统一异步模拟/API 数据层、接口合同、加载失败与并发提交处理，再接入后端认证、数据库、文件服务和通知。数据模型和接口草案在第一阶段开始前确定，并随第二阶段细化。

运营侧至少预留企业核验、商品审核、需求管理和投诉处理。支付、订单履约、会员推广和复杂推荐留待询盘撮合流程验证后按业务目标扩展。

参考：[ECHEMI 首页](https://www.echemi.com/)公开导航包含商品/供应商/询盘搜索、买家和供应商入口、用户中心、询盘管理及店铺入口。本次借鉴其信息结构，以上模型和优先级是针对本项目的建议。
