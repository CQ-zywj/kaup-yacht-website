## 1. 判定原则：什么才算"重复入口"

三条判据，命中任一条才动手删：

| 判据 | 含义 | 典型症状 |
| --- | --- | --- |
| **写唯一** | 同一字段只能有一个页面能写 | 两个页面都能保存 `tagline`，后存的覆盖先存的 |
| **读分层** | 同一实体可以有"摘要卡 / 列表 / 详情"，但**列表只能有一个** | 同一批询盘在两个页面各列一遍，排序和筛选还不一样 |
| **路径最短** | 同一任务有多条路径时，保留步数最少的那条，其余降级为引导 | 新建商品能从导航两个一级菜单进入 |

**一条红线**：删入口不等于删功能。页面只要有独立价值（对外可访问、被外部链接引用、承载 SEO），就保留页面、只删导航入口，并用跳转兜住老链接。

## 3. 七组重复入口的处置决策

### 第 1 组 · 店铺门面字段

| 项 | 内容 |
| --- | --- |
| 现象 | `company.html` 的编辑表单里嵌了 `storefrontEdit()`（`js/company.js:139`），能改 tagline / theme / logo / video / address；`store-decoration.html`（`js/supplier-settings.js`）能改 tagline / theme / logo / banner。两处都写 `supplier_profile` |
| 保留 | **`store-decoration.html`** 为唯一门面编辑入口 |
| 删除 | `company.html` 的 `storefrontEdit()` 编辑表单（`js/company.js:139-144`），改为只读摘要 `storefrontRead()` + 一个「去店铺装修」按钮 |

| 用户逻辑 | 用户的两种心智是分开的：「填公司资料」去公司页，「摆门面」去装修页。现在两边都能改同一批字段，用户不知道该信哪个，且保存会互相覆盖 |
| 验收 | `company.html` 保存后不再影响 `tagline/theme/logo/video`；装修页保存后公司页摘要同步变化 |

| `news.html` / `exhibitions.html` / `content.html` | 公开内容页，承载 SEO 与行业资讯，与供应商内容中心是"读 / 写"关系 |
| `company.html` 里 3 处「管理认证」链接 | 上下文引导，不是独立入口 |
| `dashboard` 的商品概览、最近询盘摘要 | 摘要卡不是列表，符合"读分层" |
| `product.html` 的「发起询盘」「进入店铺」 | 上下文入口，路径最短 |
| `rfq.html` 的 `inquiry` / `public` 两种模式 | 同一表单两种上下文（从商品来 / 从市场来），不是两个入口 |

## 7. 风险与回滚

| 风险 | 应对 |
| --- | --- |
| 用户找不到被删的入口 | 第 4 步之前先做跳转兜底；删除的只是导航项，页面都还在 |
| `tests/static.test.cjs` 页面清单校验失败 | 第 1 步同步更新清单，不删页面文件 |
| i18n 键被误删导致缺文案 | 本期**不删任何文案键**，只停用；等入口稳定后再统一清理 |
| 装修页字段划分引发数据不一致 | 所有字段仍存 `supplier_profile`，只是编辑位置变化，无数据迁移 |
| 删除买家视图后，历史"我的发布"数据无处可看 | `my-rfq` 增加公开需求分区后才允许删（第 3 步顺序不能反） |

回滚成本：改动集中在 5 个 JS（`common.js`、`company.js`、`rfq-market.js`、`supplier-shell.js`、`my-rfq.js`）+ 2 个页面，建议一步一个 commit，便于单独 revert。

## 8. 与后续优化的关系

入口定稿是后面所有工作的前提：

- **数据模型收敛**（账号双写、证书双模型、文件双存法）需要先确定"谁写"，入口不唯一就没法定写入方
- **后端化**的 API 权限矩阵按"角色 × 入口"设计，入口错了权限就错
- **SSR / SEO** 只对唯一对外主页生效，两个主页会让权重分散

**建议节奏**：第 1–3 步（约 2–3 天）先落，第 4 步（导航重构，约 1–2 天）单独一批，稳定一周后再动数据模型。
