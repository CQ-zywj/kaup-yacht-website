## 1. 为什么你的方案更对

我原来建议"保留装修页、公司页只读"，是从"页面职责正交"出发的。但按用户心智看，你这个划分才是对的：

| 判据 | 原方案（保留两个页） | 你的方案（合成一个页） |
| --- | --- | --- |
| 用户会怎么想 | "改标语要去装修页，改地址要去公司页"——两个地方都是"改我的店" | "我的店就一个地方改" |
| 字段归属 | 必须硬切：地址算资料、标语算门面，用户不认这套切法 | 不用切，都是"我的店铺"的一部分 |
| 覆盖风险 | 两个页面都写 `tagline/theme`，靠约定避免互相覆盖 | 结构上不可能再覆盖 |
| 入口数量 | 侧栏仍有"公司信息 + 店铺装修"两项 | 只剩一项 |

**原方案唯一的好处是页面不会变长**——这个用布局解决（见 §3），不该靠牺牲入口唯一性来换。

## 2. 目标形态

`company.html` 重命名为概念上的**「我的店铺 / My store」**，成为店铺资料与门面的唯一编辑入口。

### 2.1 分区（4 段）

| 区 | 内容 | 字段 |
| --- | --- | --- |
| ① 企业信息 | 公司中英文名、国家、城市、联系人、职位、电话、邮箱、官网、**地址**、企业类型、成立年份、员工数、主营类目、中英简介 | `company` `company_en` `country` `city` `contact` `position` `phone` `email` `website` `address` `business_type` `founded` `employees` `main_categories` `intro` |
| ② 店铺门面 | **Logo**、**Banner（≤3 张）**、**展示语（≤40 字）**、**主题**、企业视频 | `logo_file` `banner_files` `tagline` `theme` `video` |
| ③ 团队与实拍 | 团队成员（头像/姓名/职位）、企业实拍 | `team` `photo_files` `photos` |
| ④ 资质摘要 | 已通过证书的只读摘要 + 「管理认证」入口 | 读 `certifications` |

顺序理由：企业信息在前——门面里的 Logo、Banner 是"装饰公司资料"，先有资料再谈门面；且新入驻供应商的首要任务是填完资料才能发商品。

### 2.2 布局：左表单 + 右预览

原来装修页**没有预览**，合并后正好补上——这是净增益，不是妥协：

```
┌──────────────────────────────┬─────────────┐
│ ① 企业信息                    │ 店铺预览卡   │
│ ② 店铺门面（logo/banner…）     │  banner     │
│ ③ 团队与实拍                  │  logo+名称   │
│ ④ 资质摘要                    │  标语/主题色 │
│                              │ [预览店铺 ↗] │
└──────────────────────────────┴─────────────┘
```

- 桌面：右侧 sticky 预览卡，随表单变化实时更新（换主题色、换 logo 立即反映）
- 移动：预览折叠为顶部一条，点击展开
- 效果：表单再长也不会变成 6 屏盲滚动

## 4. 三个必须处理的技术风险

### 风险 1 · 草稿会丢 Banner（会真出 bug）

`js/company.js:8` 的 `companyEditFields` 是"编辑草稿"的白名单，里面**有 `logo_file` 但没有 `banner_files`**。

现在没暴露，是因为 banner 只能在装修页改、装修页不走这套草稿逻辑。一旦合并，用户在「我的店铺」传了 banner → 点「管理认证」→ 再返回，banner 会消失（草稿恢复时被过滤掉）。

**必须**：把 `banner_files` 加入白名单，并补一条测试（传 banner → 存草稿 → 恢复 → banner 仍在）。

### 风险 2 · 部分写盘产生孤儿文件

`collectCompany()` 现在是按顺序写：先 `logo` → 再 `photos`。如果 logo 通过校验写入成功、photos 因格式失败抛错，logo 已经进了 IndexedDB，但资料没保存 → 孤儿文件。

**必须**：改成先对所有待上传文件跑 `SupplierData.fileError` + `validateImage`，全部通过后再统一 `putMany`。这也是装修页原本做得对的地方（"先校验全部文件再落盘"），合并时要把它带过来，不能丢。

### 风险 3 · 长表单导致的填写疲劳

合并后表单比现在长约 40%。除 §2.2 的预览布局外，另加两条：

- 门面区的 Logo / Banner 支持"从素材库选"（复用 `SupplierShell.mediaPicker()`），避免每次都翻本地文件
- 每个分区头部显示完成状态（如「店铺门面 · 已配置」），让用户知道还差什么
