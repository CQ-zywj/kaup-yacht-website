# 改动记录：供应商侧栏分组（2026-10-29）

对应 `docs/入口收敛方案-2026-10-29.md` 第 5 组。方案见原文，本文记录实际怎么落地、与原方案哪里不同、验证了什么、留下了什么问题。

## 一、要解决的问题

侧栏 12 项平铺，全部处于同一层级：

```
店铺总览 / 我的商品 / 发布商品 / 批量导入 / 询盘收件箱 / 认证与资质 /
内容中心 / 素材库 / 我的店铺 / 财务中心 / 店铺主页 / 客户管理
```

这是「按系统有几个模块」排的，不是「按每天要做的事」排的。后果是找"改银行账号"这类低频操作要扫一遍全表；而"发商品"和"批量导入"这种强相关动作被"询盘收件箱"隔开。

## 二、最终分组

**7 组覆盖 12 个页面，一级项减少 42%**，且全部页面保留、不做合并：

| 分组 | 组内页面 | 形态 |
| --- | --- | --- |
| 总览 | 店铺总览 | 单项直达 |
| 商品 | 我的商品、发布商品、批量导入 | 折叠组 |
| 询盘 | 询盘收件箱（未读角标） | 单项直达 |
| 店铺 | 我的店铺、店铺主页、财务中心 | 折叠组 |
| 资质 | 认证与资质 | 单项直达 |
| 内容 | 内容中心、素材库 | 折叠组 |
| 客户 | 客户管理 | 单项直达 |

与方案原表的两处差异，都是被上一轮合并推翻的：

1. `company.html`（我的店铺）和 `finance.html` 原计划放「资质」组。门面字段已并入公司资料后，「我的店铺」本质是店铺配置，和"认证与资质"不是一类事；财务（结算账户）同理。两者一起移到「店铺」组。
2. `store-decoration.html` 原计划与 `storefront.html` 组成「店铺」组，但它已并入 `company.html` 且只剩跳转，不再占侧栏位。

## 三、交互取舍

方案原文写"组内用二级 tab"。实现时改为**可折叠分组**，理由：

- 若全展开（组标题 + 子项都列出），行数从 12 变 19（7 标题 + 12 链接），比原来更长，扫读负担反而增加。
- 若做成"组标题是链接 + 另设展开箭头"，点击语义会含糊（点标题是进组首页还是展开？），容易误触。
- 折叠后常态只有 7 行 + 当前组的 2~3 行，且**当前组默认展开**——进来第一眼就能看到"我在哪、同组还有什么"。

代价是跨组切换多一次点击。为压低这个代价，需求最高的两项做成了单项直达（询盘收件箱、认证与资质），点一次就到位；只有去「商品 / 店铺 / 内容」里的第二个及以后页面才需要先展开。

其它细节：

- 展开状态**不做持久化**：每次进页面只展开当前组。若记住上次展开状态，长期会退化成"全都展开"，等于回到 12 项平铺。
- 未读角标挂在「询盘收件箱」上；若将来询盘变成多项组，角标会移到组标题（`navMarkup()` 已按这个规则写）。
- `aria-expanded` / `aria-controls` 同步；组标题是 `<button>`，不参与 tab 顺序干扰，也满足 44px 触达高度。

## 四、逐文件改动

| 文件 | 改动 |
| --- | --- |
| `js/supplier-shell.js` | `ITEMS` 平铺数组改为 `GROUPS`（7 组、组内含 items）；新增 `navLink()` / `navMarkup()` / `bindGroups()`；`mount()` 用 `navMarkup()` 替换原来的 `ITEMS.map(...)`；导出 `GROUPS`，同时保留展平的 `ITEMS` 给需要整表的调用方 |
| `js/i18n.js` | 新增 3 个组标题键 `navGroupProducts`（商品/Products）、`navGroupStore`（店铺/Store）、`navGroupContent`（内容/Content）；`consoleProducts` 英文由 `Products` 改为 `My products`、`consoleArticles` 由 `Content` 改为 `Content center`，避免组名与子项名在英文下撞字 |
| `assets/supplier-ui.css` | 新增 `.console-group` / `.console-group-toggle` / `.console-caret` / `.console-group-items` 样式与展开态；`max-width:1023px` 时摊平为 `display: contents`，恢复原来的横向 chip 条 |
| 全部 `*.html` | 静态资源版本 `ws20261029c` → `ws20261029d` |

CSS 里两个容易踩的点，已按此处理：

- 窄屏摊平必须用 `:not([data-open])` 和 `[data-open]` 两个同等特异度的选择器，否则"展开组"会被基础规则 `display:block` 抢回去，横向条里出现块级断行。
- 子项链接的字号/内距用 `.console-nav .console-group-items a`（0,2,1）覆盖基础 `.console-nav a`（0,1,1），不靠 `!important`。

## 六、留下的问题（需决策）

**`publish.html` 与 `inbox.html` 没有控制台侧栏。** 这两个页面调用的是 `AccountUI.requireSupplier()` 而不是 `SupplierShell.mount()`，因此自带布局、不渲染左侧导航 —— 与 `company.html`、`storefront.html` 一致（后两者的定位是编辑页/公开页，可接受）。

结果是：从侧栏点「询盘收件箱」或「发布商品」进去后，侧栏消失，只能靠顶部导航回来。分组把这两个页面收进了组里，这个断点在组内切换时更明显。

两条处置路径，本轮**没有**擅自改，因为都超出"导航层级变两层"的范围：

1. **不动**：把这两页视为"专注模式"（发商品是任务流、收件箱是工作面），顶部导航已能返回。改动量 0。
2. **接入外壳**：让两页也走 `SupplierShell.mount()` 复用侧栏。代价是收件箱的双栏布局要在 232px 侧栏之外重新分配宽度，需要单独一轮做布局回归。
